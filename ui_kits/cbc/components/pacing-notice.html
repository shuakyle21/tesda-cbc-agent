Pacing Notice

The “long silence is normal” affordance. Token-bucket rate-limit pacing sleeps deliberately to stay inside the free tier, so multi-second gaps with no visible progress are the system working correctly.

No API field says “waiting on rate limit.” The token-bucket sleep is internal to the worker and writes no event row — nodes write events on entry and exit only. This notice is therefore client-side inference: non-terminal status and more than N seconds since the newest event.

States

< 20s since last event — nothing shown
(no notice — the activity list is updating on its own)
> 20s — pacing
Pacing LLM calls to stay inside the free-tier rate limit. This is expected — a full run takes a few minutes. 34s
> 90s — softened, still blue
Still working. This run is taking longer than usual. 2m 14s

What this must never be

rejected — do not build
Pipeline stalled. No response for 94 seconds.

Never the word “stalled”, and never red or amber at these thresholds. Nothing in the contract proves failure — the worker may simply be holding a token. Claiming a failure the system cannot observe trains the trainer to distrust the progress display, and the next real failure gets ignored.

20s / 90s are tunable constants, not design law. They are guesses until the M0 structured-output smoke test reports real free-tier rate-limit behaviour. Tune against an observed run.

Placement. Directly under the Run Progress Summary, above the activity list. Appears and disappears on a 150ms fade — it must not shove the list around jarringly.
